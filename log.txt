~ Welcome to the Performance-Aware Programming Series!
    - Code can be made performant in two ways:
    - Reducing total # of instructions
    - Increasing instructions per clock cycle
    i.e. moving instructions faster through the CPU

~ Waste
    - Python produces ~160-180 CPU instructions per addition
    - The argument is those 180 instructions are wasted,
      at runtime
    - Not doing this = reducing total # of instructions

~ Instructions Per Clock
    - Naive C loop is already at 0.8 adds per clock cycle,
    which implies >1 IPC, since incrementing the counter,
    checking it, loading the value, and doing the add is
    at least 4 instructions
    - Unrolling the loop one level goes up to ~1 add/clock
    - Naive unrolling is order-complected thus not parallel
    (But Python sums could be, since idiomatic Python is
     `sum(xs)`. But they're not, I checked. Python L)
    (See below though for sum() performance)
    - You can "unroll parallel" like so:
    A += xs[i]; B += xs[i+1]; i += 2
    This gets you more adds per clock because all 3 adds
    are independent.

~ Single Instruction, Multiple Data 
    - Another way to get more instructions per cycle: SIMD
    - Getting more instructions per cycle is dwarfed by
    waste oftentimes, but objectively can be a 2x gain
    - SIMD on x64 is called SSE: Streaming SIMD extensions
    - x64 SIMD add is called `paddd` for packed add DWORD
    - 1 paddd = 4 adds
    - DWORD = 32 bit, so if CPU can take a 128 bit value,
    it can do 4 of them in a paddd
    - The packed DWORDS inside a 128bit value are called
    "lanes". Lane 0 through lane 3.
    - It's a big CPU level bit field basically
    - It's kind of like being able to add two 4 dimensional
    vectors in constant time / in one CPU instruction
    - The value proposition of SIMD is not that it adds
    faster, you still have to add, but if there's only one
    instruction then the CPU doesn't have to perform all the
    steps in the pipeline (decoding the instruction,
    loading the inputs, resolving possible
    order-complection)
    - "We save a ton of decoding and bookkeeping time"
    - There are 3 SIMD instruction sets:
    SSE, AVX, and AVX-512. Most CPUs support SSE and AVX.
    SSE is 128 bits, AVX 256 (thus 8),
    and AVX-512 is 512 (thus 16).
    At least assuming 32 bit lane size.
    - Supposedly it's possible to get even more adds
    using smaller lane sizes, down to 8 bits of course
    - Naive loop: .8 adds per cycle
    - SSE (i.e. 128 bits into 4 lanes): 3.1 adds per cycle
    - AVX (256 but really like 2x128): 7.0 adds per cycle
    - "It actually is pretty common to get a speed increase
       roughly proportional to the width increase"
    - You can unroll the loop AND use SIMD to get up to 13.4
    adds per cycle, so the CPU can even do more than one
   SIMD add per cycle.

~ Caching 
    - load:store::read:write
    - adds can be order-complected, but having to load
    before adding is order-complection also
    - How does the CPU access values? Close to the compute
    part, there is a `register file`, which (my words) is
    like RAM for the CPU. OOMs faster of course.
    - "The register file is small, temporary storage
    designed to feed values to instructions
    extremely quickly."
    - First layer: L1 cache. Access time: 3-4 cycles(!!!)
    32 kilobytes on Casey's example chip.
        - (This sounds like a lot but every program running
    on the computer at any one time is vying for access)
    - L2 cache: ~14 cycles to access. Bigger than L1 but
    fewer bytes per cycle. 256kb on example chip.
    - L3: 80 instructions. 8mb on example chip.
    - After that it's main memory which is gigabytes.
    - "when you load data, the speed of the load is
    proportional to how many levels the CPU had to go
    to get it."
    - Depends on chip, but L1 is usually per-core, so each
    core gets 32k or whatever. L2 varies. L3 usually only
    one for the whole CPU.
    - Instructions can get loaded into a different L1 cache
    - The SIMD loop example from earlier goes from 13 to 8
    to 4 adds per cycle if you start summing amounts of 
    integers that don't fit into L1 or L2. Down to 1.4 adds
    per cycle if you have to go to main memory!

~ Multithreading 
    - The "Five factors" of performance:
        - waste (# instr)
        - instructions throughput (ILP)
        - SIMD
        - caching
        - multithreading
    - I feel like instructions per clock and SIMD are
    the same but idk
        - ILP != SIMD?
        - ILP decomplects at the instruction level
            - i.e. running more concurrent instructions
        - SIMD decomplects at the data level???
            - i.e. running one big instruction
        - ILP is more CPU level, SIMD more assembly level
        You can explicitly program for SIMD but not so ILP
        - (SIMD also reduces total instructions viz. loads)
    - "Today, since chip fabrication technology has
    gotten more and more advanced, CPU designers are able
    to pack dramatically more things on a chip than they
    used to. A single modern CPU package may contain
    multiple connected chips, and those chips might
    each contain multiple cores, each the equivalent
    of an entire CPU from early generations."
    - Because cores have their own caches, going multithread
    can be better than multiplying performance per number
    of cores, since it's kind of also multiplying your L1
    - Memory bandwidth can be a bottleneck; access to it
    may or may not get more efficient when multithreading.
    Depends on the chip.
    - "A single core can get the lion’s share of
    the bandwidth on its own. No matter how many cores we
    use, we can’t even double the bandwidth."
    - Interesting: if CPUs get better, the same code gets
    caching benefits "for free", but may not improve with
    more CPU cores, if it was single threaded originally.
    - Servers can have 100+ cores, so the multithreading
    multiplier is the only one that gets as big as Waste
     - i.e. single-core code on a large CPU is relatively
     as slow as going from C to Python
    - SIMD and IPC just cannot get these orders of magnitude
    - Also writing multithreaded code is very difficult
    (understatement)

    Note from the comments: indirectly trying to get the
    compiler to generate better code is fraught because
    "LLVM breaks codegen constantly, so something that
    generated good code in 14 may generate complete
    nonsense in 15,". Sounds like LLM "prompt engineering"

~ Python Revisited 
    - When you add up reducing waste and SIMD and caching
    and multithreading and loop unrolling and so on you
    really do get ~8,000x speedup
    - If you do the 80/20 of this you can probably still get
    like 100x to 1000x without going crazy (claim)
    - Summary of ways to make code fast:
        - Reduce waste
        - Increase instructions per clock
        - SIMD
        - Caching
        - Multithreading
    - The idea of the performance-aware 80/20 is to get
    a sense of what's really slow and where to focus to
    get the 100x even if using Python or whatever
    - I tried my own tests with `time` from fish but
    running an empty Python file takes much more time
    than adding 4096 integers so it's hard to see
    performance differences in the summation methods.
    - Very surprising: Numpy sums 10x slower than sum()?!
    - Not surprising but important: sum() over 10x faster
    than `for x in xs: sum += x`
    - Reminder that Python has typed numeric arrays:
    https://docs.python.org/3/library/array.html
    - Using typed arrays, Numpy now outperforms, in fact
    it gets roughly within 1-2 OOMs of C(!!!). Bad cache
    performance but for inputs that don't go in L1 or L2
    it's pretty close.
    - You can also use Cython which appears to be a fairly
    drop-in C FFI and call C code for hot loops.
    - Casey's performance secret: google the C FFI module
    for your runtime, basically
    - From the comments: Numpy favors its own ndarray type,
    although Casey says he tried it and was not faster than
    Python typed arrays.

~ “Clean” Code, Horrible Performance 
    - Casey replaces a class hierarchy of geometrical shapes
    with tagged unions and an enum, for performance.
    Cool, but his area function uses "width" for the radius.
    Unimportant in terms of CPU, but mildly upsetting.
    - The OOP slop code is at 35 cycles per shape to compute
    the area. Going back to C89 style enums drops to 24.
    I thought this didn't sound that bad but he makes the
    point that it's like undoing 3 years in hardware-time.
    - Rich Hickey is also pro-polymorphism over switches,
    but switches make the logic centralised and explicit...
    is it that bad? Casey makes the point having all the
    area formulae in one place makes it easy to find
    ways to factor out the math. Locality of behavior kinda.
    - With a little bit of cleverness and a lookup table
    he gets down to 3-5 cycles per shape!!!
    - Great line: "If I went all the way back to the
    iPhone 6, which is the oldest phone still showing up
    on modern benchmarks, it's only about three times
    slower than the iPhone 14 Pro Max. So we can't even
    use phones anymore to describe this difference."
    - The main thing seems to be using a lookup table instead
    of a switch. Almost feels like a compiler issue that you
    get a 10x speed boost from just that. And look for ways
    to eliminate branching by streamlining the math, which is
    architecturally impossible in a class hierarchy.
